# 知识中枢设计理念与核心架构演进

---

## 现状与核心矛盾

在基于人工智能编码助手与多智能体协作的研发流程中，工程知识库的沉淀与消费普遍面临三个核心矛盾：

- **知识维护依赖人工**：业务代码迭代高频，传统知识库依赖研发人员主动编写与手工维护，导致文档从创建起便逐渐滞后于真实系统。
- **本地知识容易过期**：开发者与本地智能体的代码仓库往往未及时拉取最新生产基线，若依赖本地陈旧知识进行排障或重构，极易产生决策偏差。
- **知识经验缺乏规范入口**：生产排障中获得的故障结论与经验证据极具价值，但缺乏平滑沉淀机制，若直接写入正式知识库又容易导致内容碎片化与冲突。

知识中枢针对上述现状确立了核心架构目标：

- **版本受控**：以 Git 仓库作为正式知识的唯一事实源。
- **视界统一**：由云主机对外提供最新只读视图，规避单机环境滞后。
- **自动闭环**：代码变更自动触发核验与检查点推进，实现增量维护。
- **规范入口**：人工与排障经验通过候选文档统一进入待审池，避免污染正式知识。

## 核心设计哲学

### 单一事实源与最新只读视界

- **正式知识代码化**：业务代码仓的知识沉淀于专属知识分支，系统级跨仓知识沉淀于主分支。全部文档采用 Markdown 格式组织，版本演化过程清晰可审计。
- **检索统一收敛于云端**：日常知识查询与排障分析统一面向云端知识中枢服务，杜绝因本地仓库未同步而读取旧知识的问题；本地仅保留特征代码分析，消灭单机环境差异。

### 单端口虚拟视图与动作级白名单隔离

系统在网络暴露与操作权限上通过 ActionDock 原生虚拟视图（Virtual Views）特性，统一收敛至 443 单一 HTTPS 端口，并基于鉴权令牌与动作级白名单进行细粒度权限管控与自动路由：

```text
           客户端 / 开发者 / 排障智能体                 维护智能体 / 派发子智能体
                        │                                          │
                        │ (HTTPS 443 / 查询令牌)                   │ (HTTPS 443 / 维护令牌)
                        └───────────────────┬──────────────────────┘
                                            ▼
                        ┌───────────────────────────────────────┐
                        │   ActionDock 单端口服务 (HTTPS 443)   │
                        │   基于 Bearer Token 自动路由虚拟视图    │
                        └───────┬───────────────────────┬───────┘
                                │                       │
            ┌───────────────────┴───┐       ┌───────────┴───────────────────┐
            │   sk 虚拟视图          │       │   skm 虚拟视图                │
            │  (动作级白名单严格收敛)│       │  (完整工程维护工具集)          │
            └───────────┬───────────┘       └───────────┬───────────────────┘
                        │                               │
        ┌───────────────┴───────────────┐   ┌───────────┴───────────────────┐
        ▼                               ▼   ▼                               ▼
   [工作区只读动作]              [候选收集动作] [工作区完整维护动作]            [候选归档与特权维护]
   - search.rg                  - collect   - search.rg / read / list       - knowledge.list / archive
   - files.read                             - write / edit / delete / move  - maintenance.sync / list
   - files.list                             - git.status / git.diff         - maintenance.publish / complete
```

- **面向查询用户的检索视图（sk）**：
  - 接入端口：统一 443 端口（原生 HTTPS），通过查询鉴权令牌自动匹配该视图。
  - 暴露策略：采用动作级白名单严格收敛，仅暴露只读检索与反馈追加动作（`workspace/search.rg`、`workspace/files.read`、`workspace/files.list`、`knowledge/knowledge.collect`）。
  - 安全保障：对外坚决不提供任何写入、编辑、删除、移动及版本控制动作，彻底杜绝外部未授权篡改或注入。
- **面向维护智能体的受控维护视图（skm）**：
  - 接入端口：统一 443 端口（原生 HTTPS），通过维护智能体专属强鉴权令牌自动匹配该视图。
  - 暴露策略：开放工作区完整维护与版本管理动作，包含文件写入、局部受控编辑、安全删除、受控移动、工作区状态审查、版本差异比对，以及待审池审核归档与双分支代码维护闭环。
  - 核心价值：维护智能体与派发的子智能体可以通过标准化结构化动作无缝执行端到端维护与编辑，无需依赖无状态的终端重定向脚本。

### 贡献单元与知识单元解耦

- **候选文档定位**：候选文档作为贡献单元保存在待审池中，承载排障上下文、证据链、故障现象与初步结论等时效性内容。
- **正式知识定位**：正式知识作为长期稳定的知识单元沉淀于知识库中，按照业务流程、架构模块、规则约束、接口契约、数据定义与运维手册六大规范目录分类落位。
- **解耦管理原则**：严禁将单篇候选文档机械地直接转为独立正式文件。维护智能体在消费待审池时，必须结合现有知识结构进行交叉验证、去重、补丁式增量修改或重构，保持知识体系严整。

### 代码变更驱动核验与检查点推进

- **变更代表核验触发**：业务代码发生提交差异仅代表需要进行知识有效性检查，并不意味着知识一定失效。若代码变更为内部重构或未改动对外行为，则无需变动文档。
- **检查点推进机制**：维护流程在完成代码审查与判定后，无论知识文档是否更新，均必须将检查点水位推进至当前最新提交。该机制确保本次代码差异已被知识体系审查覆盖，为后续巡检建立可靠基线。

### 双轨演进冲突处理

在将业务生产分支合并至知识分支的过程中，实行双轨冲突处理机制：

- **业务代码冲突自动自愈**：对于非知识文档的代码与配置文件冲突，合并策略无条件以生产分支为准，自动完成提交，杜绝代码差异阻断知识流水线。
- **知识文档冲突语义消解**：对于知识文档自身的合并冲突，脚本保留标准冲突标记并退出至指定状态码，交由维护智能体执行语义比对、消除冲突标记、合成准确内容，随后统一通过发布工具提交并推送。

### 零依赖容器化一体分发

- **容器全封装**：基于 Docker Compose 封装全部运行时环境与核心工具包，集成原生 HTTPS 服务与自动证书管理，实现宿主机开箱即用。
- **宿主机免运维**：宿主机环境无需安装语言运行时或部署额外脚本，维护智能体仅需通过 SSH 调度容器标准指令即可完成全部维护动作。

### 存储架构与数据持久化

- **运行时状态持久化**：ActionDock SDK 通过内部状态机制记录与维护仓库检查点水位，其底层物理存储位于容器内 `/root/.actiondock` 目录（包含全局状态库 `global.db` 与运行时数据库 `runtime.db`）。通过将宿主机 `${KNOWLEDGE_DATA_DIR}/state` 明确挂载至容器 `/root/.actiondock`，确保在容器重启、重新拉起或镜像重建时，检查点水位资产永不丢失，杜绝因检查点归零引发灾难性的全量重头建库。
- **宿主机持久化目录体系**：统一基于环境变量 `${KNOWLEDGE_DATA_DIR}`（默认为 `/data/knowledge`）收敛全部持久化数据卷，实现宿主机与容器运行环境彻底解耦：
  - `state/`：持久化 ActionDock 运行时状态库与检查点，挂载至容器 `/root/.actiondock`。
  - `workspace/`：持久化受控代码工程工作区与知识文档分支，挂载至容器 `/srv/workspace`。
  - `inbox/`：持久化候选知识待审池与历史归档产物，挂载至容器 `/srv/knowledge-inbox`。
  - `config/`：宿主机仓库清单配置文件目录，挂载至容器 `/etc/actiondock`。
  - `certs/`：可选的正式 TLS 证书挂载目录，挂载至容器 `/etc/actiondock/certs`。
  - `logs/`：持久化服务与维护运行日志，挂载至容器 `/var/log/actiondock`。
- **单一事实源与断点续传**：Git 代码仓库作为业务代码与正式知识的唯一事实源，结合持久化检查点数据库的水位追踪，确保维护流水线具备严谨的断点续传能力与幂等性。

## 业务流转时序

```mermaid
sequenceDiagram
    autonumber
    actor Dev as 开发者与排障智能体
    participant Cloud as knowledge-server 服务端
    participant Inbox as 知识待审池
    actor Maintainer as 维护智能体 (定时调度)
    participant Git as 代码仓库

    Dev->>Cloud: 发起只读检索与文档读取
    Cloud-->>Dev: 返回权威只读结果
    
    opt 发现排障经验或业务新事实
        Dev->>Cloud: 投递结构化候选文档
        Cloud->>Inbox: 校验格式并保存至待审池
    end

    Maintainer->>Cloud: 触发全量分支同步
    Cloud->>Git: 拉取生产分支并合并至知识分支

    alt 存在知识文档冲突
        Cloud-->>Maintainer: 返回冲突状态码与冲突报告
        Maintainer->>Cloud: 语义消解冲突并写回文件
        Maintainer->>Cloud: 执行发布工具提交推送
    end

    Maintainer->>Cloud: 执行单仓变更扫描
    Cloud-->>Maintainer: 返回差异提交区间与建库标识

    alt 存量首次建库
        Maintainer->>Cloud: 扫描源码并生成六大分类文档
        Maintainer->>Cloud: 执行发布工具推送初始知识库
    else 增量代码核验
        Maintainer->>Maintainer: 执行更新门槛与失效判定
        opt 知识失效需调整
            Maintainer->>Cloud: 最小化更新受影响文档
            Maintainer->>Cloud: 执行发布工具提交推送
        end
    end

    Maintainer->>Cloud: 推进检查点水位，结束维护轮次
```

## 架构演进与特性对比

| 核心维度 | 传统方案 | 知识中枢生产架构 | 核心价值 |
|---|---|---|---|
| 服务分发形态 | 宿主机裸机进程，依赖本地运行环境与外部脚本 | 容器一体化封装，开箱即用并自带自举服务 | 宿主机免前置依赖，环境完全隔离 |
| 网络暴露机制 | 外部网络统一开放端口，未对特权动作做切分 | 单端口多视图严格隔离，根据令牌自动路由只读检索与受控追加视图或特权维护平面 | 彻底杜绝特权接口网络越权风险 |
| 维护流程调度 | 零散执行底层版本控制命令 | 特权平面与网络隔离，由定时任务连入后调用标准工具链 | 屏蔽底层细碎操作，提供强类型契约保障 |
| 代码冲突处理 | 遇到冲突直接中断退出，依赖人工介入 | 业务代码自动对齐生产分支，知识冲突由智能体语义消解 | 大幅减少流水线中断，保障维护流畅性 |
| 发布提交机制 | 外部手工执行暂存、提交与推送 | 内置发布工具，自动处理分支切换、状态检验与签名提交 | 消除手工命令拼装错误，提交行为标准化 |
| 状态推进机制 | 缺乏全局状态记录或单机标记容易丢失 | 强制检查点水位推进机制，严格追踪代码审查进度 | 形成完整的增量检查闭环，杜绝重复与遗漏 |
