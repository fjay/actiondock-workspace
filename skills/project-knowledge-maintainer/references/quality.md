# 按实际用途复查知识

复查以重要结论、流程连接和代码导航为对象。标题齐全、元数据合法、篇数多或一句 PASS 都不能证明知识有用。

## 理解流程

- 从业务目标或别名能找到具体流程，而不只命中总览。
- 能说明谁触发、前置条件、主路径、关键分支、结果与状态变化。
- 同步/异步交接不断链，关键节点能定位仓库、文件和符号；未知外部环节明确边界。
- 拆分成多篇后，Agent 仍能看懂整体顺序、输入输出与继续查找的位置。

## 排查问题

- 从真实错误码、日志、现象或异常状态能进入相关节点。
- 已确认的失败行为与推测原因分开，能找到区分原因的检查方法。
- 说明失败时已发生什么、错误怎样传播、谁负责重试或收尾；不只描述成功路径。
- 检查方法、日志文本、关联键和恢复步骤都有实际依据。只有源码时不承诺线上状态。

## 辅助设计

- 能从拟修改的能力找到当前入口、实现、状态与对外契约。
- 公共不变量、职责边界和关键顺序有实际执行位置；不把注释承诺当成代码保证。
- 能找到相关调用方/消费者、关联流程和测试，区分已确认依赖与需要验证的影响。
- 当前事实、改动建议和历史决策分开；缺少决策记录时不推测当初为什么设计。

## 证据和导航

核对本次新增或改动的重要结论。单仓链接相对文档能解析；跨仓仓库标识能通过索引映射到源码，路径/符号真实。行号只是辅助，不以 sources 文件清单替代结论定位。

测试定义的预期与实际执行结果分开；看到一个测试不代表所有路径已验证。否定结论如“没有重试”需要检查相关调用链，否则限定到已读范围。

源码或配置存在某个跨仓关系，只能说明代码支持；不能自动证明特定环境中版本、路由、主题配置一致。

- **断链自检与就地修复实践**：
  - 在知识中枢受控维护环境中，所有文档编写或更新完成后，必须调用 `workspace/links.verify` 自动化检测相对路径死链、图片资源缺失与失效标题锚点：
    ```bash
    ad run workspace/links.verify --profile skm -- path="<repoPath>"
    ```
  - 当扫描返回存在断链（`brokenCount > 0`）时，根据返回的 `brokenLinks` 详情（包括出错文件、行号、失效路径或缺失锚点），立即调用 `workspace/files.edit` 就地修复相对路径或标题锚点，直至断链数清零（`brokenCount === 0`）。
  - 若在无 ActionDock 动作工具的环境中，可临时使用宿主文件检查与检索工具（如 `rg`）辅助核对引用：
    ```bash
    rg -n -- '业务名|事件名|错误码' docs/knowledge
    rg -n -- '关键符号' src tests
    ```
    实际词项和路径来自任务；大量或需要字面匹配的标识使用 `rg -F`，避免正则元字符改变检索含义。

## 从代码反查覆盖

按 coverage.md 对照实际入口、生产/消费方、状态读写、测试和配置，检查是否还有未归属流程或遗漏分支。核对“已发现”和“已调查”两类状态，检查 overview 是否掩盖了未展开的独立行为。

## 内容深度示例

无用：“系统具有完善的错误处理。”

有用的表述形态：“A 写入 X 后执行 B。B 失败时错误传回调用方，当前异常分支没有删除 X。重试时对已有 X 的处理由 C 决定。”A/B/C/X 都须替换为真实对象并附定位；C 未查清就记录未知，不能补写成保证。

## 图表使用

- 图只出现在 overview：仓库层一张全局结构图，系统层领域一张跨服务端到端图；index 只做检索表、flow 文档用节点表，都不放图。
- 仅 mermaid 或 ASCII 文本；引用 png/svg 等图片文件视为违规。
- 抽查派生视图约束：图上任一节点/边应能在对应流程或契约文档中找到依据；图出现文档没有的事实时，修图或补文档，二选一。
- 节点超过 25 个或含"系统A"式抽象名，要求拆分或实名化。
- 交接表与图并存：图给骨架，表给证据（契约、关联键、失败传播）；只留图不留表视为不合格。

## 报告

报告具体写了哪些流程/专题、按哪类问题试查、回查了哪些结论和引用、还有哪些候选/缺口。没有执行测试或独立 Agent 评估就不要声称完成。局部复查不宣称全仓完整。

外部实现不可访问可以形成有边界的交付；当前范围内关键调用链未调查则仍是未完成内容。给出继续调查的位置，而不只留“stale”或“待优化”。
